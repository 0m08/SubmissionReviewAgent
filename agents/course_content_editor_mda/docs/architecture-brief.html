How the MDA Editor Works

An agent that edits a course the way an instructional designer does — one topic at a time, against the learning objective, with every change shown as a diff before anything is written back. It runs on LangSmith's hosted harness, and the two things it refuses to do are as deliberate as the things it does.

01

The round trip

A course lives in a Google Sheet. The agent never edits that sheet in place. It pulls the course into a working copy, edits the working copy, shows you the diffs, and — only when you ask — writes the result to a new tab. The tab you started from is still there, untouched, when the meeting goes badly.

02

The three layers

The map first — what exists and where it runs. The next section walks a session through it in order. Three layers, each doing one job. The Streamlit page is a thin client — it holds no state worth losing. The deployment holds the conversation, the workspace and the files. The sandbox is a real Linux box, one per conversation, where the sheet scripts actually run.

The coordinator reads the request and hands each topic to an editor subagent that gets exactly one file, the user's words, and the course learning objectives. It runs in isolated context: it cannot see the other topics, cannot reach the sheet, and cannot write back. That is the mechanism that keeps a fifty-topic course from collapsing into one enormous prompt.

03

A session, start to finish

One real sweep, in the order it happens. Time runs down the page; each column is something that can act. Two moments are worth watching for: the approval gate, where the agent stops and waits, and the diff cards, which reach you from the sandbox without passing through the coordinator at all.

Beat 11 is the one people ask about. A rejection quotes the original block back by the same identity fields the commit script uses, so "no, not that one" re-edits a single block rather than re-running the topic — and nothing has been written to the sheet yet, because beat 12 hasn't happened.

04

How the agent is put together

The agent is not one long prompt. It is four layers with different lifetimes, and knowing which is which is what makes it maintainable: a change to house style, a change to how a sheet is parsed, and a change to what the agent is allowed to do are three different edits in three different places.

LayerWhat it isWhere it livesChanged by
Prompt instructions.md — the job, the workspace map, the approval rule, how to delegate Context Hub, on deploy an engineer, via deploy
Skills three SKILL.md files — sheet I/O, editing slide chunks, editing research notes, plus six writing styles /skills/, read-only mount an engineer, via deploy
Scripts nine Python scripts — prepare, present, measure, commit, auth check /opt/cce/scripts, baked into the image an engineer, via deploy + bake
Memory AGENTS.md — the team's editorial standards, accumulated /memories/agent/, Context Hub the agent, during a session

The distinction in that last column is the important one. Three layers change only when someone deploys. Memory changes while the tool is being used — which is what lets a correction outlive the conversation it was made in, and why it needs rules of its own.

Why the model does not read all of it

A course has fifty topics, three skills, six writing styles and a research corpus. Putting that in one prompt would be slow, expensive, and worse at the job. So the agent loads in layers: it always knows what exists, and reads the detail only when the task calls for it.

Memory, and why it is the layer to watch

Memory is scoped to the deployment, not to a person: one shared tree that every caller reads and every session can write. Ask the agent to stop expanding transitions, and the correction can be written once and apply for everyone afterwards. That is the feature. It is also the risk, because whatever one person's session saves is read by everyone who comes next.

Two rules keep that safe, and both are worth stating out loud in the demo. Memory holds procedural knowledge only — conventions stated in general terms, never a person, a sheet URL, or a credential. And memory carries no authority: it is treated as notes from a colleague, not as instructions, so what it says can inform an edit but can never widen what the agent is allowed to do. Permission lives in the deployment's own configuration, where a session cannot reach it.

06

The two things it refuses to do

Both of these are load-bearing, and both are easy to lose by accident. They are worth a minute each in the demo because they are the difference between a tool the content team can trust with a live course and a tool that needs checking.

07

Why hosted, and what it costs

The earlier build ran the agent inside the Streamlit session. If the session timed out mid-edit — and a fifty-topic sweep takes a while — the work went with it. Here the run executes on the server and the thread id lives in the page URL, so a refresh, a reconnect, or a laptop closing at the wrong moment all land in the same place: the work is still running, and you can still address it.

08

Six minutes, live

A run on a real course sheet, in the order that makes the design visible. Each beat shows something the previous build could not do.

  1. Paste a sheet URL and ask for something small

    "Tighten the transitions in Topic 3." No setup step, no configuration screen — the session is created on the first message.

  2. Let the tool activity run in the open

    The turn shows the scripts as they execute — reading tabs, loading slide chunks, counting blocks. Nobody has to trust a summary of what happened.

  3. Ask for the whole course

    Delegation is the moment worth watching: each topic goes to its own editor with its own learning objectives, and the subagent panels fill in parallel.

  4. Open the Review tab and reject one block

    Rejection quotes the original back to the agent by its identity fields. This is where the diff-not-a-summary decision pays off.

  5. Close the browser tab mid-run, then reopen the URL

    The strongest thirty seconds of the demo. The run kept going on the server; the thread id in the URL brings the whole conversation, workspace and files back.

  6. Commit, and show the source tab still intact

    The edits land in a new tab with every original column preserved. Then open the tab you started from and show that nothing moved.

09

Where it stands

Verified

  • Full round trip against a real course sheet: edit, present, withhold the commit until asked, write a new tab with every column intact
  • The committed notes are the edited ones — 4,407 → 3,696 words — not a re-pull of the source
  • Survival when the client disconnects mid-run
  • Five test suites: offline, auth proxy, scripts in a real sandbox, deployed behaviour, disconnect

Open

  • A merge deadlock kept an earlier run at 51 blocks in, 51 blocks out. The rule conflict behind it is fixed and deployed; the next run on that same plumbing course is the number to watch
  • The agent re-reads its editorial standards from a static file every session, and a correction in one thread never reaches the next. Consolidating what it learns across threads is the obvious next capability
